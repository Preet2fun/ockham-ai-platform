Agent Evaluation Guide

How to design evals and build the test harness that runs them, for any agentic or RAG use case in this repo. It covers defining what “good” means, finding the errors that matter, counting them cheaply and reliably, and gating every change on the result.

Implements ai-engine/CLAUDE.md §4 LangGraph · Langfuse (self-hosted) Tracks: SRE · ITSM · Security Supersedes 04-evaluation.md

How to use this guide

The guide has two parts. Part A covers design: what to measure and how to measure it. Part B covers the test harness: the machinery that runs those measurements on every change, offline and in production. Read Part A when you scope a new agent or RAG feature. Use Part B when you wire it into CI.

Every example comes from one of the three tracks (SRE, ITSM, Security), per ai-engine/CLAUDE.md §1. Four running use cases recur throughout:

SRE · agentic

Incident RCA agent

Supervisor graph that delegates to log, metric and deploy analysts and names a root cause for an incident such as INC-4471.

ITSM · agentic

Ticket triage agent

Classifies an incoming ticket, sets priority, links the affected CI from the CMDB and routes it to a resolver group.

ITSM · RAG

Service-desk KB assistant

Answers “how do I…” questions by retrieving tenant-scoped KB articles and citing them.

Security · agentic

Alert triage agent

Correlates a SIEM detection with asset criticality and recent identity and access changes, then proposes escalate or close.

Part A

Eval design

What to measure, and how to count it cheaply and reliably. Design comes before tooling. A harness that runs the wrong evals quickly is still wrong.

A1

Why agent evaluation is a different job

Traditional software is deterministic: the same input gives the same output, so one passing unit test proves the behaviour. LLMs are probabilistic. The same input can produce different outputs, so one passing run proves very little. An eval doesn't return pass or fail. It returns a rate: how often the system gets one specific thing right.

Figure A1. One unit test is enough for code. An LLM needs a rate over many inputs and runs.

Each jump up the stack adds something you must measure. You don't get to keep grading the old way.

SoftwareSingle LLM call / RAGAgent (multi-step)
Unit of evala function's outputone response (+ retrieved context)the whole task and every step
Pass criterion== expectedmeets a rubric or gold answertask completed through a sound trajectory
Methodassertions, pytestcode assertions, golden sets, LLM judge+ trajectory eval, tool-call accuracy, recovery-from-failure
Referenceexact expected valuegold answer or rubricoften reference-free: judge the path, or score in a simulated environment
Reliabilitydeterministic, run oncea rate over many inputsrun k times: must be consistently right (pass^k)

Two jumps. Going from software to an LLM, you trade exact assertions for judging quality, because there is no single right string. Going from an LLM to an agent, you add judging the process and its consistency. An agent can reach the right answer by a path you can't trust, or be right once and wrong the next four times.

Where our own datasets stop and public benchmarks start. τ-bench/τ²-bench (pass^k over real tool workflows), SWE-bench Verified, GAIA, BFCL v3 and WebArena/OSWorld show how the field evaluates agents. We don't ship them. We borrow their methods (our own dataset, a judge, a trajectory check, k runs, production monitoring), not their test suites.

A2

Define “good” yourself

Semantic tasks have no single right answer. Arithmetic does, but a postmortem summary, a KB answer or a triage rationale has many acceptable answers and degrees of quality. Before you can evaluate anything, write down what correct means for this use case. That definition is the lens you review traces through in error analysis (A3). It is a working draft, not a list of evals. Evals are chosen in A4, once error analysis shows which failures actually happen and which matter.

Rule A2.1. Don't outsource “good”. Generic vendor metrics like “helpfulness”, “conciseness” or “relevance” don't know your users. A verbose, step-by-step KB answer is right for a tenant's first-week support agent and too much for the on-call SRE who wrote the runbook. The product team owns the definition of correct, and that definition depends on context: who asked, what they will do with the answer, and what a wrong answer costs.
Rule A2.2. Correctness has several dimensions. Break “is this output good?” into separate dimensions a reviewer can look for in a trace. They give error analysis a consistent basis, so two reviewers mark the same trace the same way. A single overall verdict of good or bad hides which dimension broke.
Rule A2.3. Hard requirements become evals now. Some dimensions can't wait for error analysis because a single failure is unacceptable: tenant isolation, staying within the agent's autonomy level, refusing unsafe actions. Write these as evals straight away, before the agent ships. Every other dimension waits for A3 to show whether it fails often enough, and badly enough, to need one.

Figure A2. Breaking “a good answer” into dimensions a reviewer can look for. Only tenant safety is an eval from day one. The other five wait for error analysis. The same exercise for the SRE RCA agent gives: names a root cause · root cause is backed by queried evidence · timeline is accurate · delegated to the right analysts · no unsafe remediation advice (the last one is a hard requirement).

Figure A2b. A2 decides where to look, A3 shows what goes wrong, and A4 decides what to count. The only shortcut from A2 to A4 is for hard requirements.

Practical example · Security alert triage

Writing the definition of correct before any eval exists

“A good triage” for ALRT-2291 means: (1) the verdict (escalate or close) matches what a senior analyst would decide; (2) the rationale cites the identity-change and asset-criticality evidence the agent actually queried; (3) severity agrees with that evidence; (4) it never proposes an autonomous action above the agent's autonomy level (see design-considerations.md, L0–L4); (5) it states its uncertainty when evidence is missing.

That gives five dimensions to review against. Dimension (4) is a hard requirement, so it becomes an eval now, with a safety row in the dataset. The other four wait for error analysis. Say a SOC analyst reviews 80 triage traces. Wrong verdicts and uncited rationales turn up often, so both get evals. Severity mismatches appear twice, both on low-criticality assets, so that dimension is recorded but gets no eval yet. The review also turns up an error none of the five dimensions covered: the agent treats a service account as a human user. That becomes a sixth dimension and goes into the next review.

Keep the dimensions in the agent's design doc next to its rubric (05-agent-skills.md §4), so the critic and the evals work from the same definition.

A3

Error analysis: look at what the system actually does

In a chat window you judge each answer and fix the prompt as you go. A workflow or product has to perform well when nobody is watching, so you review many inputs and outputs systematically. Error analysis is the manual review and categorisation of the mistakes a system makes. It comes before any eval, because you can't count an error you haven't seen. The dimensions from A2 tell you where to look. Error analysis tells you what actually goes wrong there.

How deep you go depends on the stakes. A personal or internal helper needs a lightweight pass. Anything that touches a tenant, a production system or a security decision needs a deep, broad pass that continues after launch.

Lightweight mode · low stakes

One deep review, then automate

  1. Pick one representative output and review it completely against its sources, listing everything that should be there.
  2. Verify every factual claim, quote and ID against the source.
  3. Name each distinct type of error you find.
  4. Turn each type into an eval, then run those evals on the remaining outputs instead of reviewing each one by hand.

The upfront review is slow, but it saves time across the whole batch.

Production mode · tenant-facing

Hundreds of traces, three phases

  1. Collect traces: user input, system prompt, retrieved context, every tool call and intermediate step, final response, and the full exchange for multi-turn sessions. Langfuse already captures these (CLAUDE.md §3).
  2. Review hundreds of traces across varied inputs, tenants and roles, not one.
  3. Keep going after launch. Error analysis is ongoing.

With early (beta) tenants, say openly that outputs are reviewed and that you'll tell them when one was wrong.

Phase 1AnnotateLog every mistake as you see it, in a free-text note on the trace. Don't fix anything yet.
→
Phase 2CategoriseGroup the notes into named error patterns. Merge near-duplicates and count each.
→
Phase 3PrioritiseRank patterns by frequency × impact on the user, using what you know about tenants and operators.
→
OutputEval backlogPatterns you won't accept become eval candidates. Patterns you can live with get documented.

Keeping the phases separate stops a common failure: fixing a minor issue you happened to notice first while a frequent, serious one goes unseen.

Rule A3.1. Read before you write evals. Each eval must trace back to an error pattern you observed, or to a hard safety requirement. An eval for a problem you've never seen usually measures the wrong thing.
A4

Choose how to count each error

An eval is a metric that counts how often one specific error appears. There are four ways to count. Each fits a different kind of error. On a real run you use all of them together, each scoring the dimensions it suits.

Cheapest · deterministic

Code assertion

Plain code checks the output against a fixed rule. It is fast, free and consistent, like a unit test. It needs a structural way to detect the error without judgment.

  • Every quoted log line appears verbatim in the queried logs
  • Every cited KB ID is in the retrieved set
  • Output has exactly the fields the schema requires
  • No document's tenant_id differs from the caller's
  • Red-flag phrases (“typically”, “in most cases”) in a root cause
  • Tool arguments valid: types, required fields, values that exist
  • Transcript metrics within budget: turns, tool calls, tokens
Known answers

Golden dataset

Known inputs paired with the ideal output. Best when the output is small and has one correct answer: classification, routing, priority, verdicts, factual lookups.

  • Ticket → resolver group, priority
  • Alert → escalate / close
  • Query → KB article IDs that answer it
  • Are these two incidents duplicates? yes / no

Poor fit for long, open-ended outputs such as a full postmortem.

Semantic · costs a model call

LLM-as-a-judge

A second model checks the output against one narrow, binary criterion. Use it only when the error needs real judgment. See A5 for how to make it trustworthy.

  • Is this one claim supported by this evidence?
  • Does the severity match the gathered evidence?
  • Does the rationale reference evidence the agent actually queried?
Real-world signal

User & operator feedback

Explicit: thumbs, ratings, an analyst marking a verdict wrong. Users rarely say why. Implicit behaviour often tells you more:

  • Re-asking or regenerating means the answer didn't help
  • How the question was rephrased shows what was missing
  • A follow-up question means the answer was incomplete
  • An SRE editing the draft postmortem, or an agent re-routing a ticket, shows exactly what was wrong

Figure A4. Pick the cheapest method that can count the error. Go down the tree only when the method above it can't express the check. Try more than one method on the same error and keep the one that best agrees with your own review.

Rule A4.1. Code first. For every new error pattern, first look for a structural signal that code can count. Reach for a judge only when no such signal exists.
Rule A4.2. Decompose until a golden set fits. A complex output (a full RCA) doesn't fit a golden dataset. Its sub-steps often do: “did it pick the right failure domain?”, “are these two alerts the same incident?”, “is this the right resolver group?”. Build small golden sets for those steps.
Rule A4.3. Filter with code, then judge. Judges are expensive even with small models. Use a cheap code check to choose which items reach the judge.

Figure A4b. Code handles the clear cases for free. The judge sees 8 claims instead of 42, which cuts judge cost by about 80% on this run.

Golden datasets: what to watch. They are the easiest place to start (a spreadsheet of inputs and expected outputs counts). The errors they surface show what bad looks like, and corrected outputs added back show what good looks like, which helps you build the rubric. They have two limits: it's hard to predict production inputs before launch, and they're tedious to maintain. A golden set that isn't refreshed from production (B8) slowly stops matching real usage.

A5

Judges you can trust

The usual objection is: “if I can't trust the first model, why trust the second?” You trust a judge because it was designed and checked to be trusted. Four rules, then the operational details.

Rule 1

Make the task small

Give the judge a much narrower job than the model under test. Don't ask “is this RCA good?”. Ask “is this one claim supported by this evidence?”.

Rule 2

Binary criteria

Ask for yes/no or pass/fail, never a 1–5 score. Binary verdicts from domain experts track real quality better, and models give binary answers more consistently than calibrated scales. Give the judge one exit besides pass and fail: cannot determine (A5.1).

Rule 3

Align with humans

Compare the judge's verdicts against human labels on the same items. Adjust the prompt until they agree. Measure the agreement (TPR/TNR) and record it.

Rule 4

Expect judge error

No judge is perfect. Report its error alongside the metric, and correct the reported rate for it (A9).

Several simple judges beat one complex judge. For the security alert triage agent, run three separate binary judges: “does the rationale cite the identity change it queried?”, “does severity match the asset criticality returned?”, “does the response stay within the agent's autonomy level?”. Don't run one judge that scores “triage quality”. When a separate judge fails, you know exactly which dimension broke.

Why binary, concretely. Score the same SRE postmortem draft twice against “root cause is evidence-cited”. A 1–5 judge can return 3 one run and 4 the next. The draft didn't change. Only the judge's arbitrary line between “mostly cited” and “cited” moved. Pass/fail removes that line: either the draft names a root cause backed by a log or metric the agent queried, or it doesn't. Binary verdicts also match the critic in 05-agent-skills.md §4, which returns APPROVE/REVISE on the same rubric.

Rule A5.1. Let the judge say “cannot determine”. A judge returns PASS, FAIL or CANNOT_DETERMINE. The third option is for when the evidence it was given doesn't settle the question, for example a claim cites a log line that was truncated in the transcript. Forcing a verdict there just makes the judge guess. Cannot-determine units are left out of the pass rate's denominator, sent to the human review queue, and counted: report the cannot-determine rate next to the metric. A rate above about 10% means the rubric or the judge's input is unclear, so fix that before touching the agent. Calibration (rules 3 and 4) tracks these units separately from agreement. Every verdict that counts is still binary.

Known judge biases and mitigations. LLM judges favour certain positions, longer answers, and their own model family. Mitigate with a tight rubric, temperature=0, pairwise comparison instead of absolute scoring where possible, and, for anything that gates a release, a panel drawn from a different model family than the agent under test. A same-family panel doesn't fix self-preference bias, because that bias is specific to the model family. In the multi-agent system from 01-orchestration.md §6, the writer runs on Model C, so its critic and judge run on Model B, a different family. That way the judge isn't predisposed to favour the writer's own phrasing.

1Draft the rubricOne binary criterion per judge, with pass and fail examples.
→
2Human-label a sample20–50 items, labelled by a domain expert (SRE lead, SOC analyst, ITSM lead).
→
3Run the judgeSame items, temperature=0. Compute TPR and TNR against the labels.

Practical example · SRE RCA judge calibration

Catching a false-positive judge before it gates a PR

Pull 20 closed incidents. An SRE lead marks each postmortem draft's root-cause section correct or incorrect. The judge runs on the same 20 drafts and passes 3 drafts the SRE marked wrong. All 3 name a cause that sounds plausible but cite a dashboard the agent never queried. That gives TNR = 4/7 ≈ 0.57, well below the bar. The fix is in the rubric: “the cited evidence must appear in the provided tool-call log”. Re-run, TNR rises to 0.86, and only then is the judge allowed to block merges.

A6

Evaluating RAG: score retrieval and generation separately

A RAG answer can fail in two places that look the same from outside. Retrieval returned the wrong context, or generation misused the right context. Score each stage separately. Otherwise you'll tune the prompt to fix a retriever problem, or the reverse.

Figure A6. Eval tap points along the KB assistant's RAG pipeline. Retrieval and context checks are mostly code and golden sets, so they're cheap. Generation needs a narrow judge for groundedness. Outcome comes from behaviour.

Symptom in the answerRetrieval evalGeneration evalWhere to fix
Wrong steps for VPN MFA resetrecall@5 missgroundedRetriever: chunking, embeddings, query rewrite, metadata filter
Wrong steps for VPN MFA resetKB-1043 retrievedungrounded claimGenerator: prompt, context ordering, model
Confident answer to an unanswerable questionno relevant docdidn't abstainGenerator: abstention instruction plus a golden “unanswerable” row
Answer mentions another tenant's runbookforeign docn/aRetrieval filter. Severity: blocker. A tenant leak fails the whole run.

Two more dimensions for RAG and investigation agents. Coverage: did the answer include every fact a good answer must contain? Each row lists its required facts. Code checks them when they're IDs or values, and a per-fact binary judge checks them otherwise. Source quality: did the answer rely on authoritative sources? That means the current KB article over a superseded one, and telemetry the agent queried over a past incident it half-remembers. For example, an answer to “how do I rotate the VPN client certificate?” can be fully grounded in KB-2210 and still fail coverage because it leaves out “restart the VPN agent”, a required fact for that row.

Rule A6.1. Tenant isolation is a zero-tolerance code assertion. Every retrieved document must carry the caller's tenant_id (root CLAUDE.md §3, ai-engine/CLAUDE.md §2.1). It isn't a rate you try to improve. Any single failure blocks the merge, whatever the other scores are.
A7

Evaluating agents: outcome, process, trajectory, recovery

For agents, the counting methods from A4 apply at four layers of every run. Outcome-only eval is necessary but not sufficient. An agent that reaches the right verdict by guessing, or by calling an API eight redundant times, passes an outcome eval and fails on trajectory or cost.

LayerWhat it checksUsual methodNeeds
OutcomeIs the final answer right?code assertion / golden setground truth
ProcessIs the reasoning grounded in the evidence it gathered?LLM judge, binarythe explanation + tool results
TrajectoryRequired tools and subagents called, forbidden ones not called, within the step budget, no loops or redundant calls, and every call's arguments valid (types, required fields, values that exist). Order is checked only where it's a hard dependency, such as verifying identity before granting access.code over the tool-call log and tool schemasthe run's trace / LangGraph state
RecoveryWhen a tool failed mid-run, did it retry and still answer, or cascade or fabricate?code + golden, on fault-injected rowsa fault injected into the fixture

Reasoning layer vs action layer

An agent can fail in two places that look the same from the final answer. The reasoning layer is the model's planning, decomposition and tool choice. The action layer is the tool calls themselves and what the external systems return. A correct plan with a bad execution fails, and so does a perfect execution of a wrong plan. Evaluate each layer on its own and together. Otherwise “80% task completion” tells you nothing about where the other 20% went wrong.

Figure A7. The same security triage run, split by layer. Every layer writes to the trace, so an eval can be pinned to the layer that failed instead of to the final answer.

Rule A7.2. Grade the outcome, not the exact path. Don't assert an exact sequence of tool calls. Valid agents find different routes, and a sequence check punishes a better route as harshly as a broken one. Assert what must hold on any acceptable route: required tools present, forbidden tools absent, hard dependencies in order, arguments valid, budget respected, and the outcome correct.

Long trajectories: judge the steps, not only the path

The trajectory check is code over the tool-call log, and it confirms the path has the right shape: required tools called, forbidden ones avoided, within budget. On a 30-step run, the path can have the right shape while one step is still wrong. For example, step 4 misreads a metric, later steps build on that mistake, and the final answer happens to land anyway. For long runs, add a step-level judge that asks one binary question per step: “given the state before this step, was this action, and the agent's reading of its result, correct?”

  • Same judge rules as A5: narrow, binary, from a different model family than the agent, and calibrated against human-labelled steps before it gates anything.
  • Filter with code first (A4.3). Judge only the steps that code flags: the first step after a tool error, steps whose cited evidence isn't in the tool results, and steps where the working hypothesis changes.
  • The unit is a step. Report the share of steps judged sound and, for debugging, the index of the first bad step.
  • The input is the checkpointed state at each step. This is the explicit Reflect/Update State write required by CLAUDE.md §2.2.
Practical example · SRE RCA, row sre-1

A lucky run that outcome and trajectory both pass

The run takes 28 steps. The trajectory check passes, because it delegated to the right analysts within budget. Code flags 5 steps for review, and the step judge fails step 4: “treated a 2% error rate as baseline; the retrieved dashboard shows a 0.1% baseline.” The final answer still named connection pool exhaustion, so the outcome eval passed too. Only the step judge shows that this run got lucky, and the same mistake would give a wrong answer on the next incident.

Multi-turn agents: test with a simulated user

A single-input dataset row can't test a conversation. An agent that asks clarifying questions, such as the ITSM service-desk assistant or a triage agent that goes back to the requester, needs a simulated user. That's a second model, or a script, that plays the requester from a persona with a hidden goal. It answers only what it's asked, and the conversation ends when the goal is met or the turn budget runs out.

What a simulated-user row contains
  • Persona and opening message
  • Hidden facts, revealed only when the agent asks for them
  • Behaviour rules, e.g. corrects the scope at turn 3
  • Success condition on the end state, plus a turn budget
What to measure
  • Task success on the end state (code or golden), e.g. the ticket was routed correctly
  • Turns to resolution against the budget
  • Redundant questions: asking for information already given (binary judge)
  • Safety and tenant rules hold on every turn, not only the first
# datasets/itsm-triage/v2026-10-19/itsm-mt-04.yaml
id: itsm-mt-04
mode: multi_turn
tenant: customer_b
simulated_user:
  persona: "Store manager, non-technical, in a hurry"
  opening: "card machine broken again"
  hidden_facts:                       # revealed only when the agent asks
    scope: "all 3 POS terminals, card payments only"
    since: "about 09:00"
    error_text: "payment declined"
  behaviour: [answers_only_what_is_asked, "turn 3: says the kitchen display is fine"]
  model: { family: different-from-agent, version: pinned, temperature: 0.3 }
success:
  end_state: { route_to: payments-oncall, priority: P2 }
  max_turns: 8
evals: [end_state_golden, turns_to_resolution, redundant_question_judge, no_cross_tenant]
Rule A7.1. The simulator is part of the fixture. Version it with the dataset, and pin its model, version and temperature. Otherwise two runs aren't comparable. Use a different model family from the agent. Run each conversation k times (pass^k, A9), because both sides are non-deterministic. Read a sample of transcripts to confirm the simulator stays in persona and doesn't hand over hidden facts unasked. That's the same check-the-checker rule as B6.1.

Partial credit through binary milestones

A security triage run that queried the identity changes and the asset criticality but then gave the wrong verdict is better than one that guessed without querying anything. A single pass/fail at task level hides that difference. Keep every grader binary, and get partial credit from several milestone graders per task. Then choose how they combine.

The agent testing pyramid

The shape is the same as in software testing; the implementation differs. Most tests should be fast and cheap. A common mistake is running only the slow end-to-end tests. Catching search_logs returning the wrong lines at Layer 1 costs almost nothing. Catching the same bug only at Layer 3 means paying for a full graph run with a real model first.

A9

Numbers you can defend

Eval results come from small samples, and judges make mistakes. Three corrections keep the numbers honest.

1 · Sampling noise

Gate on the interval, not the point estimate

A pass rate over 10–20 rows has real sampling noise. One flaky row moves it 5–10 points. Compute a Wilson interval and gate on its lower bound. Example: 16/20 = 80% looks like it clears an 80% gate, but the 95% interval is about 58%–92%. The honest lower bound (58%) does not clear it.

2 · Non-determinism

pass^k: right on all k attempts

An agent that's independently 90% right, run k=5 times, gets all five right only 0.9⁵ ≈ 59% of the time. pass^5 reports 59%, not the 90% a single lucky green run suggests. For an agent running unattended in production, 59% is the number that matters.

3 · Judge error

Correct the rate for judge accuracy

With calibrated TPR (judge says pass when truly pass) and TNR (judge says fail when truly fail), estimate the true pass rate as (observed + TNR − 1) / (TPR + TNR − 1). Report both the raw and the corrected number.

4 · Resilience

Recovery rate as an SLO

Across all runs where a fault fired (a flaky incident-insight or threat-intel call), what fraction recovered (retry, then a correct answer) instead of cascading or fabricating? Track it per track like a reliability SLO, not as an anecdote.

pass@k vs pass^k: pick the one your product promises

pass@k is the chance that at least one of k trials succeeds: 1 − (1 − p)k. It rises with k. pass^k is the chance that all k trials succeed: pk. It falls with k. At k = 1 they're equal. By k = 10 one approaches 100% and the other approaches 0%.

Figure A9. The same agent, measured two ways. At 75% per trial, three trials all succeed only 42% of the time, while at least one succeeds 98% of the time.

Phase 4Pre-merge offline

Run the full supervisor graph with the real model against the full dataset through the harness (Part B), scored at all four layers (A7). A row passes only if outcome holds and the judge passes and the trajectory is clean and, where a fault was injected, recovery holds. The gate fails the build if the regression suite's Wilson lower bound drops below its threshold or a regression task newly fails, any metric regresses, a zero-tolerance eval fails, or cost or latency goes over budget (B7).

How a regression sneaks in, and how the gate catches it. Someone proposes a cost optimisation: “the multi-agent system is expensive, let the supervisor answer directly instead of delegating.” An outcome-only eval might pass a plausible summary. The trajectory eval sees no delegation, and the outcome and judge evals see a generic answer instead of the deploy/pool-size fact the fixture requires. The gate blocks the merge. The fix is to restore delegation and re-run the same harness. The scorecard proves it's fixed.

Determinism is a contract. A PR that changes prompt, model, tool or graph structure must update the affected fixtures in the same PR, or CI fails on drift instead of on a stale baseline.

Deliverable: a Langfuse experiment run linked to the PR, with the gate result and scorecard visible in CI.

Phase 5Pre-production

Reliability pass: pass^k and recovery rate. These are expensive per commit, so run them nightly or weekly on a sampled subset and state the sample, e.g. “3 of 10 rows, including both flaky cases”. Silent truncation misrepresents coverage.

Deliverable: reliability scorecard (pass^k with a confidence interval, plus recovery rate per track) attached to the promotion decision.

Phase 6Production

Online eval on live traffic: sample a share of real runs, score them with reference-free judges (no ground truth exists in production), and attach the score to the Langfuse trace (B8). SRE example: score live RCA traces for groundedness before the true root cause is confirmed. Security example: score live triage traces for internal consistency (does severity match the gathered evidence?). This surfaces drift as soon as a new alert type appears that the offline set never covered.

Deliverable: a live Langfuse dashboard with a rolling online score and an alert rule on drift.

Phase 7Continuous loop

A production drift or a human “this was wrong” becomes a new offline fixture. It re-runs the Phase-4 gate, which either confirms the fix or blocks a bad one. Example: a production trace where metrics_analyst cited a stale baseline becomes fixture sre-7, with that exact evidence attached.

Deliverable: the dataset grows from production every week. The agent can only get better, never silently worse.

Part B

Test harness design

The machinery that runs Part A's evals on every change. It needs to be generic enough to reuse across every agent and RAG use case, and transparent enough that every number traces back to the output that produced it.

B1

What the harness is for

By hand, one eval round means running every input through the system, saving every output, running every eval against every output, and tallying the results. You repeat all of it for every prompt or model variant. That is fine for a handful of inputs in a spreadsheet and impossible at production scale. The harness automates this loop so a full comparison is one command and one CI job.

Job 1

Run

Call the system under test (a LangGraph graph or a RAG chain) for every input, k times, and record outputs and traces.

Job 2

Transform

Reshape each output into the units each eval expects: claims, citations, tool calls, verdicts.

Job 3

Score

Run every eval module and aggregate the results into an error rate per eval for the whole run.

Job 4

Compare & explain

Compare baseline and variant side by side, list every failure in readable form, and link each one to its trace.

B2

Architecture

Figure B2. Harness architecture. The runner knows how to call the system but nothing about how outputs are judged. The eval modules know how to judge but nothing about how outputs were produced. That separation is what keeps the harness generic.

Rule B2.1. Each eval is a self-contained module. One module per error type, behind one standard interface. The harness passes it outputs and gets verdicts back without knowing its internals. Adding an eval never touches the runner.
Rule B2.2. Separate running from scoring. Persist raw outputs before scoring. Changing an eval then means re-scoring stored runs, which costs no model tokens for code evals, instead of re-running the agent.
Rule B2.3. One harness, many systems. Each system under test (RCA graph, triage graph, KB RAG chain) plugs in through a small task adapter. Datasets, evals, reports and the gate are shared.
Rule B2.4. Langfuse is the system of record. Every harness run is a Langfuse experiment, and every row carries its trace ID, per CLAUDE.md §3. Local reports are views over the same data. Emit agent traces using the OpenTelemetry GenAI semantic conventions, on the same OTel stack as root CLAUDE.md §5, so the trace data isn't tied to one backend. Verify the current convention names and Langfuse's OTLP ingestion at implementation time.
Rule B2.5. Every trial starts from clean state. Trials must be independent, or k trials are really one trial counted k times. Leftover state causes correlated failures, and it can also inflate scores when a trial reads what an earlier trial left behind. In our stack that means: a fresh thread_id per trial, so no checkpoint is reused; a per-trial LangGraph Store namespace (eval/<experiment>/<trial>) that's dropped afterwards; read-only, versioned pgvector and context fixtures; and fault injection keyed per trial. The output cache in the runner is for re-scoring a finished trial when only an eval changes. It must never feed one trial's output into another trial. Example: an RCA trial that can see a previous trial's episodic-memory write “INC-4471 root cause: connection pool” will pass without investigating.

2. Eval module interface

from typing import Protocol, Literal, Iterable
from dataclasses import dataclass

@dataclass
class Verdict:
    unit_id: str          # e.g. "itsm-017#run2#claim3"
    passed: bool | None   # binary; None = cannot determine (judges only, Rule A5.1)
    evidence: str         # human-readable reason; goes straight into failures/<eval>.md
    trace_id: str         # Langfuse trace for click-through

class EvalModule(Protocol):
    name: str                                    # "kb_citation_valid"
    kind: Literal["code", "golden", "judge"]
    zero_tolerance: bool                         # True → any failure blocks the gate (e.g. tenant leak)

    def applies_to(self, item: "DatasetItem") -> bool: ...
    def prepare(self, run: "RunRecord") -> Iterable["EvalUnit"]: ...   # transform: output → units
    def evaluate(self, unit: "EvalUnit") -> Verdict: ...

prepare() is the transform step: a groundedness eval splits an answer into claims, a citation eval extracts KB IDs, and a trajectory eval reads the tool-call log. The error rate for a module is failures ÷ units across the run.

B4

Designing the input set

The harness is only as good as its inputs. A tidy, happy-path input set produces a flattering baseline that production will contradict. Design inputs that give the errors you care about a chance to appear.

Make them realistic
  • Include production mess: typos, pasted stack traces, two services in one ticket, a reporter who corrects themselves mid-message.
  • Ambiguous attribution: “the deploy” when two deploys landed that hour.
  • Spread across tenants, roles and time windows, with tenant headers set per row.
Make them hard on purpose
  • Rows built to make a label hard (a P1 phrased like a P3, a benign alert that looks malicious).
  • Unanswerable rows for RAG (no KB article exists).
  • Fault-injected rows (tool timeout, 503, empty result) and safety rows (requests above the autonomy level).
  • Adversarial signals per synthetic-rca-eval-design-considerations.md.
  • Multi-turn rows with a simulated user (A7) for any agent that holds a conversation.
Keep them representative
  • Seed from real traces where possible (B8). Mark source: on every row.
  • Track coverage by traits and difficulty, not only row count.
  • Hold out a split that prompt tuning never sees, so you don't overfit the dev split.
Keep them maintained
  • Version the dataset. Every result names the version it ran on.
  • Freeze tool responses as context fixtures so offline runs are deterministic.
  • Retire rows that no longer match the product, and record why.

Size guide. Personal or internal helper: 10–20 typical cases. Layer-3 golden paths: 10–20 per agent. A tenant-facing harness set: 50–150 rows that grow weekly from production. Statistical power comes from units, not rows. 40 rows × 3 runs × ~4 claims gives the groundedness eval roughly 480 units.

Is each task fair?

Rule B4.1. Two experts, one verdict. A task is well specified when two domain experts, working independently, reach the same pass/fail verdict on the same output. If an SRE lead and a second SRE disagree, rewrite the task or its criteria before using it.
Rule B4.2. Every task has a reference solution. This is a known-good output that passes every grader on the task. It proves the task can be solved, and it proves the graders are wired correctly. Run reference solutions through the harness whenever a grader changes.
Rule B4.3. Passable by following instructions. Everything a grader assumes has to be stated in the task. If the grader expects a failure_domain field, the task or schema must ask for one.
Rule B4.4. 0% means suspect the task first. A task that fails across many trials is more often broken (ambiguous, unsolvable, or a buggy grader) than impossible. Read its transcripts before you conclude the agent can't do it.
Practical example · ITSM triage, row itsm-031

The ticket reads “kitchen display froze during lunch rush” and expects route_to: payments-oncall. Two ITSM leads label it independently: one says payments, the other says store-devices. B7

CI gate, cadence and cost

The gate

A PR merges only if all four hold: (1) every zero-tolerance eval (tenant isolation, autonomy-level safety rows) passes with 0 failures; (2) the regression suite holds: its Wilson lower bound is at or above a high threshold (e.g. 0.95), and no task that passed on the baseline now fails on all three of k = 3 re-runs (one failure in three counts as flakiness and goes to the nightly pass^k run). The capability suite is reported on the PR but doesn't gate (B9); (3) no eval regresses beyond tolerance versus the main-branch baseline, even if the overall number goes up; (4) median cost per task and p95 latency stay within budget versus the baseline (e.g. no more than +10%), unless the experiment config explicitly accepts the trade-off and records why.

Pinned model versions, and upgrades go through the gate

Every model the agent uses is pinned to an exact version ID in config, for every role, including judges and simulated users. Never use a “latest” alias, because the provider can change what it points to without warning. That makes a model upgrade an explicit event. It runs as a variant (B5) through the same gate, then the nightly pass^k and recovery pass, before promotion. Changing a judge's model also means re-calibrating it (A5) before it can gate anything.

def rule_evaluator(*, input, output, expected_output, **kwargs):
    # substring match kept short for illustration; prefer a structured field (Rule B6.2)
    ok = expected_output["expect_outcome"].lower() in output["answer"].lower()
    return Evaluation(name="outcome_correct", value=1.0 if ok else 0.0)

def trajectory_evaluator(*, input, output, expected_output, **kwargs):
    expected = set(expected_output.get("expect_delegate_to", []))
    ok = expected.issubset(set(output["tools_called"]))
    return Evaluation(name="right_delegation", value=1.0 if ok else 0.0)

def judge_evaluator(*, input, output, expected_output, **kwargs):
    passed = llm_judge(input["question"], expected_output, output["answer"])   # binary, temp 0, other family
    return Evaluation(name="judge", value=1.0 if passed else 0.0)

result = dataset.run_experiment(
    name="exp-2026-10-16-sre-rca-01",
    task=task,
    evaluators=[rule_evaluator, trajectory_evaluator, judge_evaluator],
)
# CI gate: zero-tolerance evals == 0 failures AND wilson_lower(regression_pass_rate) >= 0.95
#          AND no regression task newly failing on 3/3 re-runs AND no eval regresses > 0.02
#          AND median cost/task and p95 latency within +10% of baseline (unless accepted in the experiment config)

Keeping cost under control

  • Cache outputs by (input hash, git ref, prompt version). Re-scoring after an eval change costs no agent tokens.
  • Filter with code before judging (Figure A4b). Judges see only the units code couldn't decide.
  • Use small judge models on narrow binary tasks, but only once calibrated.
  • Tier by difficulty: cheap rows per PR, expensive multi-step rows nightly (synthetic-rca-eval-design-considerations.md #10).
  • Record cost and latency per run in the result record. A variant that's 3× the cost for +1 point is a product decision, not an automatic win. That's why cost and latency are the gate's fourth condition: the trade-off has to be accepted explicitly.

Online harness and the feedback loop

Offline proves the agent can reason correctly on frozen evidence. Online proves it still holds up on real, messy production data (the Axis 1/Axis 2 split in synthetic-rca-eval-design-considerations.md principle 6). The same eval modules run in both places. Online uses only the reference-free ones, because production has no ground truth.

# Inside/around the live agent call:
with langfuse.start_as_current_observation(as_type="span", name="itsm.ai.sre.incident_investigate") as span:
    answer = supervisor_graph.invoke({"messages": [{"role": "user", "content": live_question}]})
    if sampled(rate=0.10):                                   # sample online judging to control cost
        passed = reference_free_judge(live_question, answer)  # same binary judge module as offline
        span.score_trace(name="online_groundedness", value=1.0 if passed else 0.0)

Figure B8. The feedback loop: evaluate, catch, diagnose, fix, re-evaluate. Human feedback from an SRE, ITSM agent or SOC analyst is the highest-value signal, and it attaches to the trace the same way a judge score does.

Practical example · Security alert triage, online

Drift on a new alert type

A new SIEM rule starts emitting OAuth consent-grant alerts that no offline row covers. The online “severity matches evidence” judge drops from 96% to 78% within two days, and the Langfuse alert fires. Error analysis on 40 of those traces shows the agent treats consent grants as low-criticality because the asset lookup returns no host. Six of those traces become rows sec-21…sec-26. The fix (an identity-scoped criticality lookup) has to pass them, along with every older row, before it merges.

Track the offline/online gap. A large gap means the offline set no longer represents production, and the next dataset refresh should target it.

Watch cost online too. Track cost per task or conversation, per tenant, in Langfuse. Alert on any run above a set multiple of the median (e.g. 3×), which usually means a loop or an oversized context. Treat sustained cost drift the same way as quality drift: the expensive traces go through error analysis and become dataset rows, and the fix goes through the gate.

Layers of defence

No single method catches everything. Think of the methods as slices of Swiss cheese: each has holes, and a failure only reaches users when the holes in every slice line up. Use all six slices, each at the stage where it works best.

B9

Capability vs regression suites

Suites do two different jobs, and mixing them under one threshold weakens both. A capability suite asks what the agent can't do well yet. It should start with a low pass rate, which gives you something to improve against. A regression suite asks whether the agent still does everything it could do before. It should sit near 100%, so any drop is a break. A capability score of 40% is healthy, and a regression score of 95% is an incident.

Figure B9. The suite lifecycle. Capability work climbs, graduated tasks protect what's been gained, and saturation keeps the capability suite worth running.

Practical example · Security alert triage, OAuth consent-grant alerts

After the drift in B8, the six new rows sec-21…sec-26 go into the capability suite. The baseline passes 2 of 6. Three experiments later the identity-scoped criticality lookup passes 5 of 6, and after two clean nightly pass^3 runs those five graduate into the regression suite. From then on, a PR that breaks any of them is blocked. The sixth row stays in capability until it graduates too.

Rule B9.1. Eval-driven development. Define a planned capability as a capability suite first, then build until it climbs. Writing the task also tests whether the requirement is concrete. If two experts can't agree on pass/fail for it (Rule B4.1), the requirement isn't ready to build. Low-scoring capability suites also show which bets pay off as soon as a new model version lands (B7, pinned versions).
