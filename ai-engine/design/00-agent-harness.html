Agent Harness Guide

The principles and reference design for the infrastructure that wraps the model in every agent we build for SRE, ITSM and Security. It covers the 11 harness components, how one turn of the loop works, and the seven decisions every agent design has to make explicitly.

Agent = Model + Harness. If it isn't the model, it's the harness.
Applies to every agent in ai-engine/ LangGraph · Langfuse (self-hosted) Tracks: SRE · ITSM · Security Frames pillars 01–05

01

The model is rarely the problem

A ReAct loop, a few tools and a good system prompt work in a demo. Past roughly ten steps, the same setup starts to fail. The model forgets what it already did, tool calls fail silently, and the context window fills with noise. Swapping in a stronger model rarely fixes this. Fixing the infrastructure around the model does.

Figure 1. The same bare loop. A short task with three scoped tools stays clean. A long incident with an unscoped tool pile loses track of its own actions.

Published results back this up. One team changed only the infrastructure around an unchanged model and moved from outside the top 30 to 5th on TerminalBench 2.0. Across that benchmark, harness changes alone have moved agents more than 20 ranking places. The harness is the product.

Principle 1. When an agent fails, look at the harness before blaming the model. Check context, tool scope, state, error handling and verification first (see §10).
02

What a harness is

Definition. The agent harness is the complete software infrastructure that wraps a model: the orchestration loop, tools, memory, context management, state persistence, error handling and guardrails. The agent is the goal-directed, tool-using, self-correcting behaviour users see. The harness is the machinery that produces it. “We built an incident agent” really means “we built a harness and pointed it at a model”.

Figure 2. The computer analogy, mapped to our stack. The context window is scarce RAM, so the harness decides what loads into it and when.

Three levels of engineering

Figure 3. A harness isn't a wrapper around a prompt. Prompt work and context work are both inside it, together with everything that keeps a long-running autonomous loop safe and recoverable.

03

The 11 components of a production harness

The components fall into three rings around a stateless model. The runtime runs each turn. The capabilities give the loop hands, memory and focus. Safety & scale keeps the loop correct and bounded as tasks get longer and riskier.

Figure 4. The harness has layers. It isn't one wrapper. Requests pass inward through guardrails, the runtime turns them into model calls, and every action leaves through the capability and safety rings.

Runtime ring
1

Orchestration loop

The heartbeat. Each turn of the Thought → Action → Observation (ReAct) cycle assembles the prompt, calls the model, parses the output, runs any tool calls, feeds the results back, and repeats until done. Mechanically it's often just a while loop. The complexity is in what the loop manages.

Guidance
Keep the loop simple and let the model reason. Every loop has an explicit goal-achieved check and a hard ceiling (turns, tokens, wall-clock time).
In our stack
A LangGraph graph: an llm_call node ↔ a tool_node through a conditional edge, with recursion_limit set on every invoke. Every node emits a Langfuse span named itsm.ai.<track>.<op>.
Example
The SRE RCA supervisor loops at most 25 steps. If it hits the ceiling, it returns “inconclusive, evidence so far: …” instead of guessing.

5

Prompt construction

Builds what the model sees at each step: system prompt, tool definitions, skill/rubric text, memory, conversation history and the current input, in a deliberate priority order.

Guidance
Use a fixed priority stack, highest first: (1) platform policy (tenant scope, autonomy level, safety rules) · (2) tool definitions for this step only · (3) agent skill and rubric · (4) task input · (5) retrieved evidence · (6) compacted history. Put critical instructions at the start and repeat the task at the end, because content in the middle of a long context gets lost.
In our stack
Prompts are versioned in Langfuse. Skills load by progressive disclosure: a short index is always present, and the full skill text loads only when it's used.
Example
The ITSM triage prompt always starts with “tenant: customer_b, role: agent, autonomy L1: propose routing, never reassign”.

6

Output parsing

Turns model output into a decision. Use native tool calling: the model returns structured tool_calls, not free text to scrape. If there are tool calls, run them and loop. If there are none, that's the final answer.

Guidance
Final answers are schema-constrained (Pydantic). On a schema failure, retry once with the original prompt, the failed output and the parse error, then fail loudly.
In our stack
Structured output goes into the typed LangGraph State, never as a raw string between nodes (CLAUDE.md §2.1).
Example
The security triage agent's final output is TriageVerdict(verdict: Literal["escalate","close"], severity, evidence_ids: list[str], rationale). The evals in 04-evaluation.html read these fields directly.
8

Error handling

Errors compound. A 10-step task at 99% per-step success finishes cleanly only about 90% of the time. The harness decides what happens to each kind of failure so one bad call doesn't sink the run.

Guidance
Classify every failure: transient → retry with backoff, at most 2 retries · model-recoverable → return the error to the model as a tool result so it can adjust · user-fixable → pause for a human · unexpected → raise, record and debug. Catch errors inside tool handlers so the loop keeps running.
In our stack
Tool wrappers return ToolMessage(status="error", …). User-fixable failures call LangGraph interrupt(). Unexpected ones become Langfuse error spans. Recovery is measured by the recovery eval (04-evaluation.html A7).
Example
threat-intel returns 503 → backoff retry succeeds. A CMDB lookup returns “CI not found” → the model receives that and searches by hostname instead of inventing a CI.
Capabilities ring
2

Tools

The agent's hands. Each tool is a schema (name, description, typed parameters) injected into context. The tool layer handles registration, argument validation, sandboxed execution, result capture, and formatting results as readable observations.

Guidance
Give each step the smallest tool set it needs. More tools usually means worse tool choice. Descriptions say when to use the tool, not only what it does. Return compact observations, not raw payload dumps.
In our stack
Tools are exposed through MCP. Each specialist subagent has its own scoped set, roughly 10 or fewer. Every call is risk-gated per 03-tools.md.
Example
The identity-access subagent sees only iam.recent_changes, iam.role_grants and iam.user_profile, not the 30 tools the whole platform offers.

3

Memory

Works at several timescales. Short-term memory is the current session. Long-term memory persists across sessions and is loaded in tiers.

Guidance
Use three tiers: (1) a small index that is always loaded (one short line per entry) · (2) detailed topic records loaded on demand · (3) raw history reachable only through search. Writes go through an explicit write policy, so memory doesn't fill with unverified claims.
In our stack
LangGraph Store with tenant-namespaced keys for cross-thread memory. Episodic incident memory lives in pgvector, per 02-memory.md. Never read across tenants.
Example
The SRE agent's always-loaded index names “checkout-service: 3 past pool-exhaustion incidents”. Full postmortems load only when the hypothesis matches.

4

Context management

This is where many agents fail without any visible error. Performance drops noticeably when key content sits in the middle of a long window, and instruction-following degrades as context grows, even in very large windows.

Guidance
Aim for the smallest set of high-signal tokens. Four techniques: compaction (summarise near the limit; keep decisions and open questions, drop redundant tool output) · observation masking (hide old tool outputs, keep the calls visible) · just-in-time retrieval (carry IDs, load content only when needed) · subagent delegation (a subagent explores widely and returns a 1–2k-token summary).
In our stack
Retrieve, rank and trim before injecting (CLAUDE.md §2.1). Evidence goes into state as IDs plus short excerpts.
Example
The logs_analyst greps 2 GB of logs but hands the supervisor 12 cited lines and a 300-token summary.
7

State management

What the run knows right now, held so the run can resume, be inspected and be replayed.

Guidance
Use typed state with explicit merge rules, checkpointed at every step boundary. For work that spans sessions, keep a structured progress record (what's done, what's next, open questions) instead of relying on chat history.
In our stack
A LangGraph State TypedDict with reducers and a Postgres checkpointer. thread_id is the incident, ticket or alert ID. Time-travel replay is used for debugging failed runs.
Example
An INC-4471 investigation pauses for SRE approval overnight and resumes the next morning from the same checkpoint, with every hypothesis already ruled out still in state.
Safety & scale ring
9

Guardrails & safety

Checks at three points: input (before the first step), output (on the final answer) and tool (every call). A tripwire stops the run immediately.

Guidance
Keep permission enforcement separate from reasoning. The model decides what to attempt. The tool layer decides what is allowed. Use three stages: (1) trust set at session start (tenant, role, autonomy level) · (2) a permission check before every tool call · (3) explicit human confirmation for high-risk actions.
In our stack
Tenant and role come from X-Tenant-ID / X-User-Role, never from the model. Autonomy levels L0–L4 come from design-considerations.md, with L0/L1 as the default. High-risk steps call interrupt().
Example
“Auto-revoke the flagged user” trips the tool guardrail at L1. The agent proposes the revocation and pauses for a SOC analyst.
10

Verification loops

This is the main difference between demo and production agents. Giving a model a way to check its own work is reported to improve quality 2–3×.

Guidance
Use computational checks first (schema validation, “does every cited ID exist in the tool results?”, tests). Use inferential checks (a separate critic or judge) for semantic qualities. Think of them as guides, which steer before acting (rubric in the prompt), and sensors, which observe after acting (checks on the output).
In our stack
The writer + critic pattern with a per-agent rubric (05-agent-skills.md §4). The same check modules run in the offline harness and online scoring (04-evaluation.html).
Example
Before the RCA draft returns, a code check confirms every cited log line exists. Then the critic (from a different model family) approves or sends it back for revision against the rubric.
11

Subagent orchestration

Spawning specialists, either as agents-as-tools (the specialist handles a bounded subtask and returns) or through handoffs (the specialist takes over control).

Guidance
Prefer agents-as-tools: the parent keeps control and gets a condensed result back. Each subagent has an isolated context and its own tool scope. Split into subagents only for a clear reason (see decision 1 in §8).
In our stack
A supervisor graph calls specialist subgraphs. Specialists never call each other. Independent evidence gathering fans out in parallel with Send.
Example
The security triage supervisor fans out to identity-access and asset-criticality in parallel and merges two short summaries.

One turn of the loop

The loop is simple mechanically. Each step in it carries real infrastructure.

Figure 5. One cycle. The permission check happens in step 4, errors come back as results in step 5, and compaction triggers in step 6.

Walkthrough · Security alert triage, ALRT-2291, turn 2 of 5

What each step actually does

StepWhat happensHarness component
1 AssemblePolicy (tenant customer_a, L1), 3 identity tools, triage rubric, alert payload, turn-1 summary, task restated at the end⑤ ④ ③
2 InferModel asks for iam.recent_changes(principal="svc-batch-07", window="24h")①
3 ClassifyA tool call is present, so execute⑥
4 ExecuteArguments validated. The read-only call is allowed at L1. Runs through MCP with tenant headers.② ⑨
5 Package“1 grant: role db_admin on prod-db-03 at 02:14 by user j.doe (no change ticket)”. About 40 tokens instead of the raw 6 KB JSON.② ④
6 UpdateAppended to state. The turn-1 raw SIEM payload is masked and its ID kept.④ ⑦
7 LoopTurn 3 checks asset criticality. Turn 5 emits TriageVerdict, which then goes through the verification loop.① ⑩

Why every step matters: errors compound. End-to-end success is roughly per-step success raised to the number of steps.

end-to-end success
–

Long-running work across many context windows

Some work outlasts one context window: a multi-hour incident, or a postmortem built over several sessions. Use a two-phase pattern. Continuity comes from durable records, not chat history.

Session 1 · initializer

Set up the work

  • Create a progress record in Store keyed by the incident ID
  • Write the task list: hypotheses to test, evidence to gather
  • Create the first checkpoint
Every later session · worker

Pick up, advance, record

  • Read the progress record and checkpoint, not the old transcript
  • Take the highest-priority open item and work it
  • Write the result and a short summary, then checkpoint

How frameworks implement the pattern

The major frameworks have converged on the same core loop. They differ in where they think control should live. We use LangGraph only (ai-engine/CLAUDE.md §3). The comparison shows which ideas we borrow, not a menu of options.

The minimal LangGraph harness every agent here starts from (verify signatures against the LangGraph docs at implementation time):

from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.prebuilt import ToolNode

def llm_call(state: MessagesState):                       # ① loop body, ⑤ prompt built upstream
    return {"messages": [model.bind_tools(scoped_tools).invoke(state["messages"])]}

def route(state: MessagesState):                          # ⑥ output classification
    return "tools" if state["messages"][-1].tool_calls else END

g = StateGraph(MessagesState)
g.add_node("llm_call", llm_call)
g.add_node("tools", ToolNode(scoped_tools))               # ② tools, errors returned as ToolMessage (⑧)
g.add_edge(START, "llm_call")
g.add_conditional_edges("llm_call", route, ["tools", END])
g.add_edge("tools", "llm_call")
agent = g.compile(checkpointer=postgres_checkpointer)     # ⑦ state

agent.invoke(
    {"messages": [("user", alert_payload)]},
    config={"recursion_limit": 25,                        # ① hard ceiling
            "configurable": {"thread_id": "ALRT-2291"},   # ⑦ resumable by alert ID
            "callbacks": [langfuse_handler]},             # every step traced
)
06

Scaffolding: design the harness to shrink

Figure 6. The scaffolding metaphor. The harness makes work possible that the model can't do alone today, and parts of it should come down as models improve.

Implication

Harness complexity should fall over time

One production agent team rebuilt its harness five times in six months, and each rewrite removed complexity. Elaborate tool definitions became general-purpose ones, and “manager” agents became simple structured handoffs.

Caution

Models and harnesses co-evolve

Models are trained with particular harnesses in the loop. A model tuned on one tool layout can get worse when you change it. Change tool shapes deliberately, and re-run the eval harness when you do.

Test

The future-proofing check

If a stronger model makes the agent better without adding harness complexity, the design is sound. If every model upgrade needs new scaffolding, the harness is fighting the model.

Principle 2. Every planning step, router or helper agent in a harness should have a reason to exist that can be tested. When a model upgrade lands, run the eval harness with that scaffolding removed. If the scores hold, delete it.
07

Harness thickness

Thickness is how much logic lives in the harness versus in the model. It's the central architectural bet: how far you trust the model, and how much you encode in code.

Figure 7. The thickness spectrum. LangGraph sits toward the thick end, which we need for auditable, tenant-scoped, autonomy-gated agents. We keep it honest by making each node thin.

Principle 3. Thick where it's a contract, thin where it's reasoning. Encode in the graph whatever must hold no matter what the model thinks: tenant scope, autonomy gates, interrupt() approvals, termination ceilings, verification before output. Leave everything else to the model inside a node: which hypothesis to try next, which query to run, how to phrase the rationale.

The seven harness design decisions

Every agent design has to make these seven calls explicitly. There's no universal right answer, only trade-offs. The highlighted leaves are our defaults. Deviating from a default is allowed, but write down why in the agent's harness spec (§9).

Figure 8. The seven decisions, with our defaults highlighted.

#DecisionTrade-offOur defaultDeviate when
1Single vs multi-agentMulti-agent adds routing calls, context loss at handoffs, and typically 3–10× tokensGet the most out of a single agent firstAny of the three triggers: context protection, parallelisation, specialisation (00-pillars-overview.md §4), or about 10+ overlapping tools
2ReAct vs plan-and-executeReAct adapts but costs more per step. Plan-and-execute is faster (reported up to 3.6×) but adapts less.Supervisor plans and fans out with Send. Specialists run ReAct inside their scope.Fully known, fixed procedures can be a deterministic pipeline with no ReAct
3Context strategyAggressive compaction saves tokens. Rich context improves recall but costs more.Lean: compaction, observation masking, IDs + excerpts, 1–2k-token subagent summaries. Keeping reasoning traces over raw tool output keeps accuracy while cutting tokens.A short, high-stakes task with a small evidence set can carry it all
4Verification designComputational checks are deterministic and cheap. Inferential checks catch semantic issues but add latency.Computational checks always. A critic or judge only where judgment is needed. Same modules as the eval harness.Never ship without at least one computational check on the final output
5Permission architecturePermissive is fast and risky. Restrictive is safe and slower.Restrictive: start at L0/L1, interrupt() for any writeRaise autonomy per tool, only after offline and online evals show it's safe (design-considerations.md)
6Tool scopingA full toolkit is flexible. A minimal set per step gives better choices.Minimal per step and per subagent, loaded lazilyExploratory read-only agents may get a wider read set
7Harness thicknessThin trusts the model. Thick encodes control.Thick graph for contracts, thin nodes for reasoning (Principle 3)Re-assess at each model upgrade (Principle 2)

Harness spec for a new agent

Before writing graph code, every new agent gets a harness spec: one page that answers all 11 components and all 7 decisions. Keep it next to the agent's code. It's the design-review artifact and the input to the eval dataset (04-evaluation.html A2, A10 Phase 1).

Worked example · Security alert triage agent

harness-spec.yaml

agent: security.alert_triage
span_prefix: itsm.ai.security.alert_triage
goal: "Decide escalate | close for one SIEM alert, with cited evidence"
autonomy: L1                     # proposes; never acts (design-considerations.md)

decisions:                       # the seven decisions (§8)
  agent_count: multi             # trigger: parallelisation (identity + asset lookups are independent)
  reasoning: supervisor plan-and-execute; specialists ReAct
  context: lean                  # raw SIEM payload masked after turn 1; IDs + excerpts in state
  verification: [computational: evidence_ids_exist, schema; inferential: critic (other model family)]
  permissions: restrictive       # read-only tools only; any revoke/disable → interrupt()
  tool_scoping: per-subagent     # identity-access: 3 tools; asset-criticality: 2 tools
  thickness: thick graph, thin nodes

components:                      # the eleven components (§3)
  loop:        {recursion_limit: 25, wall_clock: 120s, exit_on: [no_tool_calls, tripwire, budget]}
  prompt:      {stack: [policy, tools, skill+rubric, alert, evidence, history], task_repeated_at_end: true}
  parsing:     {final_schema: TriageVerdict, on_schema_error: retry_once_with_error}
  errors:      {transient: backoff x2, tool_error: return_to_model, missing_permission: interrupt, other: raise}
  tools:       {via: MCP, scoped: true, risk_gated: true}
  memory:      {store_namespace: "tenant/{tenant}/security/assets", episodic: pgvector prior detections}
  context:     {compaction_at: 70%, subagent_summary_max_tokens: 1500}
  state:       {schema: TriageState, checkpointer: postgres, thread_id: alert_id}
  guardrails:  {input: tenant+role from headers, tool: per-call allowlist, output: no autonomous action text}
  verification:{before_return: [evidence_ids_exist, critic_approve]}
  subagents:   {pattern: agents-as-tools, fan_out: Send, peers_never_call_each_other: true}

evals: see 04-evaluation.html (dataset rows sec-1..sec-6 + fault + safety rows)
10

When an agent fails, check the harness first

Find the symptom in the Langfuse trace, then go to the component.

Symptom in the traceLikely componentFirst fix to try
Repeats a tool call it already made④ context, ⑦ stateKeep tool calls visible when masking outputs. Record “done” items in state.
Ignores an instruction late in a long run④ context, ⑤ promptCompact earlier. Restate the task and constraints at the end of the prompt.
Picks the wrong tool, or invents one② tools (scope)Fewer tools per step. Say in each description when to use the tool.
A failed call ends the whole run⑧ error handlingReturn the error to the model as a result. Retry transient failures with backoff.
States facts no tool returned⑩ verificationAdd a computational evidence-ID check before output. Add a critic for groundedness.
Runs until it hits the turn limit① loopMake the goal-achieved check explicit. Return a partial result with the evidence so far.
Attempts an action above its autonomy level⑨ guardrailsEnforce at the tool layer, not in the prompt. Add an interrupt() gate.
Supervisor loses detail from a specialist⑪ subagentsUse a structured summary schema for subagent returns, with IDs plus findings.
Unparseable final answer⑥ parsingUse native structured output. Retry once with the parse error.
